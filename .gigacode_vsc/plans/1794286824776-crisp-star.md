# Анализ нарушений SOLID в проекте KostyaBank

## Краткое резюме
Проект — WPF-банкомат с MVVM-архитектурой. Нарушения SOLID присутствуют во всех 5 принципах, наиболее критичные — DIP и SRP.

---

## 1. S — Single Responsibility Principle (Одна ответственность)

### Нарушение: `MoneyStorage` (Models/MoneyStorage.cs)
**Проблема:** Класс смешивает 3 ответственности:
- Хранение данных (Dictionary<int, int>)
- Бизнес-логика (алгоритм выдачи купюр `TakeMoney`, подсчёт `SumMoney`)
- I/O (чтение/запись Excel через `LoadFromExcel`/`SaveToExcel`)

**Где:** Строки 14-185. `TakeMoney` содержит алгоритм жадного распределения номиналов + запись в Excel.

### Нарушение: `CardStorage` (Models/CardStorage.cs)
**Проблема:** Аналогично — хранение данных + бизнес-логика + I/O в одном классе.
- `LoadFromExcel`/`SaveToExcel` — Excel I/O (строки 73-135)
- `AddCard`/`RemoveCard`/`Clear` — бизнес-логика

### Нарушение: `AppViewModel` (ViewModels/AppViewModel.cs)
**Проблема:** Класс содержит:
- Навигацию между экранами (6 методов `Show...`)
- Хранение `MoneyStorage` (строка 11)
- Логику выхода (`ExitApp`)
- Логирование (`Log.Write` в `ShowServiceView`)

**Рекомендация:** Вынести I/O в отдельные репозитории (`IMoneyStorageRepository`, `ICardStorageRepository`), оставить в моделях только бизнес-логику.

---

## 2. O — Open/Closed Principle (Открыт для расширения, закрыт для модификации)

### Нарушение: `AppViewModel`
**Проблема:** Каждый новый экран требует **модификации** класса — добавления нового метода:
```csharp
public void ShowCardEntry() { ... }
public void ShowMainMenu(Card card) { ... }
public void ShowGetForm(Card card) { ... }
public void ShowShowForm(Card card) { ... }
public void ShowServiceView() { ... }
public void ShowMoneyStorage() { ... }
public void ShowCardStorage() { ... }
```
Класс растёт линейно с количеством экранов.

**Рекомендация:** Использовать навигационный сервис с маршрутизацией, или `IViewRegistry` с регистрами экранов.

### Нарушение: `Money` (Models/Money.cs)
**Проблема:** `PossibleAmounts` — публичная field-коллекция, номиналы захардкожены.
```csharp
public List<int> PossibleAmounts = new() { 50, 100, 200, 500, 1000, 5000 };
```
Любое изменение номиналов требует модификации класса.

## 3. L — Liskov Substitution Principle (Подстановка подтипов)

### Потенциальное нарушение: `CardFormViewModel` → наследники
**Проблема:** `OnPrintReceipt()` вызывается внутри `ExecuteAction` при `PrintReceipt == true`, даже если наследник не переопределил метод. Метод `virtual`, но вызывается из базового класса.

```csharp
// CardFormViewModel.cs, строка 27-32
_actionCommand = new SimpleCommand(() =>
{
    ExecuteAction();
    if (PrintReceipt)
        OnPrintReceipt();  // Вызывается всегда, даже если не переопределён
}, () => CanExecuteAction);
```

**Рекомендация:** Либо сделать `OnPrintReceipt` абстрактным (если все наследники должны печатать), либо переместить логику печати в наследников.

---

## 4. I — Interface Segregation Principle (Разделение интерфейсов)

### Нарушение: прямая реализация `INotifyPropertyChanged`
**Проблема:** `INotifyPropertyChanged` реализован напрямую в `Money`, `BaseViewModel`, `CardFormViewModel`. Нет сегрегации — все классы получают полный интерфейс, хотя им нужен только `PropertyChanged`.

**Рекомендация:** Для MVVM это не критично, но можно выделить:
```csharp
public interface IUpdatable { event PropertyChangedEventHandler PropertyChanged; }
```

---

## 5. D — Dependency Inversion Principle (Зависимость от абстракций) ★ НАИБОЛЕЕ КРИТИЧНОЕ

### Нарушение: все ViewModel создают зависимости через `new`

#### `CardEntryViewModel` (строки 25-28):
```csharp
public CardEntryViewModel(AppViewModel appViewModel)
{
    _computer = new Computer();      // Прямая зависимость
    _cardStorage = new CardStorage(); // Прямая зависимость
    _appViewModel = appViewModel;
}
```

#### `GetFormViewModel` (строка 21):
```csharp
_printer = printer ?? new Printer(); // Прямая зависимость
```

#### `ShowFormViewModel` (строка 16):
```csharp
_printer = printer ?? new Printer(); // Прямая зависимость
```

#### `CardStorageViewModel` (строка 25):
```csharp
_cardStorage = new CardStorage(); // Прямая зависимость
```

#### `ServiceViewModel` (строки 18-34):
```csharp
// Два конструктора с разными сигнатурами — workaround для разных сценариев
public ServiceViewModel(AppViewModel appViewModel) { ... }
public ServiceViewModel(Card card, AppViewModel appViewModel) { ... }
```

**Рекомендация:** Внедрить зависимости через конструкторы:
```csharp
public interface ICardRepository { Card? GetCardByNumber(string number); }
public interface IMoneyRepository { int TakeMoney(int amount); ... }
public interface IReceiptPrinter { string SaveWithdrawDoc(...); ... }

public class CardEntryViewModel : BaseViewModel
{
    private readonly ICardRepository _cardRepository;
    private readonly ICardStorageRepository _cardStorageRepository;
    
    public CardEntryViewModel(
        ICardRepository cardRepository,
        ICardStorageRepository cardStorageRepository,
        AppViewModel appViewModel)
    {
        _cardRepository = cardRepository;
        _cardStorageRepository = cardStorageRepository;
        _appViewModel = appViewModel;
    }
}
```

## Приоритеты исправления

1. **🔴 DIP** — внедрить интерфейсы для `Computer`, `CardStorage`, `Printer`, `MoneyStorage`. Это даст тестируемость и гибкость.
2. **🟡 SRP** — разделить `MoneyStorage`/`CardStorage` на модель + репозиторий.
3. **🟡 OCP** — навигационный сервис вместо метода `Show...` в `AppViewModel`.
4. **🟢 LSP/Isp** — мелкие правки.
